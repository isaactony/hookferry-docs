# Case study: AI-ready documentation for a developer CLI and API

**Project:** Hookferry docs (a fictional webhook CLI and REST API)
**Role:** Technical writer and information architect
**Stack:** Mintlify, MDX, OpenAPI 3.1, Git
**Scope:** 30 hand-written pages, 13 generated API reference pages, a custom agent skill, and an AI test harness

## The problem

Developers now ask an AI assistant before they open the docs, and coding agents read the docs directly. When docs are written only for people who scroll and skim, AI tools give confident wrong answers: invented CLI flags, wrong retry counts, or code that parses JSON before verifying a signature.

The goal was to build a documentation site that people and AI tools can both use to get **correct, complete answers**, and to prove it with a repeatable test instead of a claim.

## Approach

### 1. Information architecture designed for retrieval

AI tools retrieve one page, or one chunk of a page, at a time. So the structure follows two rules: **one topic per page**, and **one job per section**.

- The Documentation tab uses a Diátaxis-style split: Get started, Concepts, How-to guides, CLI reference, Troubleshooting, and Resources. "How do I…" questions land on a guide, and "what is…" questions land on a concept page.
- Troubleshooting is organized by **symptom** (`401` on every event, `✕ connection refused`, "the provider sent it but my app never got it"), because users paste symptoms into AI tools, not causes.
- The API reference is generated from an **OpenAPI 3.1 spec**, so field names, limits, and error codes have one source of truth. Four hand-written pages (authentication, errors, pagination, rate limits) cover what a spec can't explain.

### 2. Writing rules that survive being read out of context

Every page follows a short standard:

- A specific `title` and a one-sentence `description`. The description becomes the page's summary in `llms.txt`.
- Descriptive headings. A heading is often the only context an AI chunk keeps, so "Retry schedule for HTTPS destinations" replaces "Details".
- Prerequisites stated at the top of every task.
- Links instead of "as mentioned above".
- Numbers instead of adjectives: "up to 8 delivery attempts over about 22 hours 36 minutes", not "several retries".
- A controlled vocabulary with a glossary. *Retry* (automatic) and *replay* (on request) never mean the same thing.

### 3. AI-readiness features

| Feature | Purpose |
| :-- | :-- |
| Contextual menu (copy page, view as Markdown, open in ChatGPT, Claude, or Perplexity, connect MCP in Cursor and VS Code) | One-click handoff from any page to an AI tool |
| Site-wide agent instructions (`markdown.instructions`) | Every Markdown page tells agents the non-negotiables, for example "verify signatures against the raw body" |
| Custom `skill.md` | A one-page capability summary for agents: tasks, commands, and the rules that are easy to get wrong |
| Prompt component with an agent-only Markdown version | People get a copy button. Agents get a clean fenced command instead of prose that runs into the page |
| `llms.txt`, `llms-full.txt`, `.md` pages, and the `/mcp` server | Generated by Mintlify from the structure above |

### 4. Docs-as-code quality gates

Every change runs through `mint validate` (MDX, navigation, and OpenAPI rules, plus a strict build), `mint broken-links`, and `mint a11y`. Code samples are tested: the Express and Flask signature-verification examples were extracted from the page and run against valid, tampered, and stale requests.

## What the checks caught

| Check | Finding | Fix |
| :-- | :-- | :-- |
| `mint broken-links` | 14 links to generated API pages used the wrong URL pattern | Found the real routes from the local preview and corrected every link |
| `mint a11y` | The dark-mode brand color had a 2.53:1 contrast ratio (minimum 3:1) | Changed it to a color with 5.80:1 |
| Markdown export review | The Prompt component's text ran straight into the page body in `.md` output, so agents couldn't tell where the prompt ended | Split the content into human and agent versions with Mintlify's `Visibility` component |
| Running the code samples | Both samples passed: valid → 200, tampered → 401, stale → 401 | No change needed |

## Results: the 10-question AI test

A separate AI agent, with no memory of writing the docs, answered 10 realistic user questions using only the Markdown export of the site. The product is fictional, so the agent couldn't fall back on training data: every answer had to come from the docs.

**Round 1:** 10 of 10 answers were correct and none were wrong. 3 answers were correct only through inference that a weaker tool could miss. The most important: asked "How do I delete a source using the CLI?", the agent answered correctly that no command existed, but only because it noticed one was missing. Nothing in the docs said so. The test also found two ambiguities and a race condition in the CI example.

**Fixes:** 8 targeted content changes across 8 pages. For example, a new "Delete or rename a source" section states that the CLI can't do it, the retry wording is now identical everywhere, and a contradiction about expired events is resolved.

**Round 2:** A new agent retested the fragile questions plus two that targeted the fixed ambiguities: 5 of 5 correct with high confidence, and no contradictions between pages. Asked about deleting a source from the CLI, it now answers "You can't" and cites three pages that say so.

| | Round 1 | Round 2 |
| :-- | :-- | :-- |
| Correct answers | 10 / 10 | 5 / 5 retested |
| Fragile answers (correct only by inference) | 3 | 0 |
| Contradictions between pages | 1 | 0 |

Full question-by-question results: [ai-question-test.md](ai-question-test.md).

**Round 3 (live MCP retrieval):** After deployment, the 10 questions went to the site's live MCP search tool, the first thing any connected AI client calls. 8 of 10 returned the answer page first. One was partial and one missed. Both failures came from headings that didn't match how users phrase questions, so the fixes added a question-shaped FAQ entry and put "401", "Express", and "Flask" into the troubleshooting page's title and headings. After fixes: RETEST_PENDING.

The takeaway for clients: **a reading test shows the answer exists, and a retrieval test shows an AI can find it.** Both are needed.

## What this shows

- **Information architecture that serves people and machines.** The same structure that helps a person scan a page helps an AI retrieve the right chunk.
- **Measurable AI readiness.** AI quality is tested with real questions and fixed in the content, not handled with prompt tricks.
- **A docs-as-code workflow.** Validation, link checks, accessibility checks, and tested code samples run on every change.
